## Project overview

**ResumeIQ** is an AI-powered resume screening assistant for recruiters, built as an internship project by Diya Kamboj (TPM / AI engineer).

**Product goal:** Help recruiters upload multiple resumes, extract structured candidate information, analyze job descriptions, match and rank candidates with explainable, evidence-backed scores, and query candidates through an AI recruiter copilot agent.

**Product name:** ResumeIQ — "AI Resume Screening for Recruiters".

**Current status:** Frontend demo with mock data. The real Azure-backed MVP implementation exists on a separate branch (`origin/Aasrith`) but is NOT merged into the working branch — see "Branch situation" below.

### MVP scope (current priority)

2. Resume parsing
3. Job description analysis
4. Candidate matching and ranking

### Level 1 features (after MVP)

## Architecture

### Current branch (as checked out)

Frontend-only. TanStack Start SSR app where every feature is a convincing UI over mock data:

```
Browser
  │  TanStack Start SSR + hydration
  ▼
Routes (src/routes/*) + app-shell + copilot
  │
  ▼
Client state (src/lib/app-state.tsx)  ← fake upload pipeline (setInterval)
  │
  ▼
mock-data.ts  ← 248 deterministic-random candidates, fake JD analysis, rule-based copilot
```

- Upload pipeline is simulated in `src/lib/app-state.tsx` (`setInterval` advancing `queued→uploading→ocr→parsing→complete`, ~2.5% random failures).
- Scoring is `scoreOf`/`rankCandidates` over fabricated category scores in `src/lib/mock-data.ts`.
- Copilot (`src/components/copilot.tsx`) matches keywords against the mock pool — no LLM call.

### Reference architecture (on `origin/Aasrith` — the target design)

```
Browser
  │  React Query → createServerFn (RPC, CSRF-protected)
  ▼
Server handlers (src/lib/api/jobs.ts, resumes.ts)
  │
  ▼
Service layer (src/lib/server/)
  ├─ pipeline.ts                 # ingestion queue, SHA-256 dedupe, concurrency
  ├─ document-intelligence.ts    # Azure DI OCR (async submit + poll)
  ├─ pdf-text.ts                 # local text-layer extractor (node:zlib)
  ├─ resume-parser.ts            # Azure OpenAI (JSON-schema) + heuristic fallback
  ├─ jd-analyzer.ts              # Azure OpenAI requirement extraction + fallback
  ├─ matching.ts                 # 3-signal scoring engine (keyword/semantic/AI)
  ├─ screening.ts                # async screening run + progress polling
  ├─ ai\                         # provider seam (ChatClient/EmbeddingClient + Azure impls)
  ├─ store-types.ts              # Store interface (persistence seam)
  └─ store.ts                    # JSON-file store (.data/, Node-only)
  │
  ├── Azure AI Document Intelligence   (OCR)
  ├── Azure OpenAI chat                (parse, JD analysis, candidate analysis)
  ├── Azure OpenAI embeddings          (semantic similarity, disk-cached)
  └── Heuristic fallbacks              (offline mode works with zero Azure creds)
```

**Key design decisions in the reference implementation (preserve these):**
- **Deterministic-first, LLM best-first:** keyword + embedding signals score the whole pool; the expensive LLM pass runs best-first over the top `SCREENING_AI_ANALYSIS_LIMIT` (default 50) to bound cost.
- **Three-signal blending** per category: keyword, semantic (cosine on Azure embeddings, disk-cached), and AI (LLM). Blend weights shift when the AI signal is absent (0.6/0.4 vs 0.3/0.2/0.5).
- **Evidence tracing is first-class:** per-requirement verdicts (`met|partial|missing` + quoted evidence), `SignalBreakdown` per category, `source` on every evidence item.
- **Weighting is separable:** raw category scores stored server-side; recruiter weights applied client-side for instant re-ranking.
- **Graceful degradation:** every Azure path checks `capabilities()` and falls back to heuristic parsers / keyword-only matching; the UI labels which engine produced each result (`parseEngine`, `analyzedBy`, `aiAnalyzed`).
- **Client/server boundary:** server modules are imported dynamically *inside* `createServerFn` handler bodies so the compiler strips them from the client bundle (an import-protection plugin rejects top-level shared imports).

**Known architectural risks (documented in the planning assessment):** JSON-file store + in-memory hashes + in-process background screening are single-process and won't survive serverless. Needs a real datastore, blob storage for resumes, and a durable queue worker before cloud deployment. No auth, single tenant, PII in plaintext on disk.

## Coding conventions

Follow the style already in the codebase. Key points observed:

- **TypeScript strict mode with** `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noPropertyAccessFromIndexSignature`. This means array access returns `T | undefined` — the codebase uses non-null assertions (`arr[0]!`) and `?.`/`??` pervasively. Match that idiom.
- **Path alias:** `@/` maps to `src/` (e.g. `@/lib/utils`, `@/components/ui/button`).
- **Named exports** for functions/components; `export const Route = createFileRoute("/path")({ head, component })` for routes.
- **`cn()`** from `@/lib/utils` for conditional classnames (Tailwind merge).
- **Comments explain *why*, not *what*.** The codebase has thoughtful, decision-documenting comments (e.g. why the store is a `globalThis` singleton, why server modules are dynamically imported, why h3 errors are normalized). Preserve and continue this style — especially around non-obvious AI/Azure behavior.
- **Model output safety:** LLM responses are treated as untrusted — coerce with explicit helper functions (`str`, `strArray`, `numOr`, `coerce`) and never trust the shape directly. This pattern is in `resume-parser.ts`/`matching.ts` on Aasrith; replicate it for any new LLM call.
- **No `any`:** use `unknown` + narrowing, explicit type unions, and `as const` for literal unions.
- **Tailwind v4** (CSS-first config in `styles.css`); shadcn/ui `new-york` style; design tokens via CSS variables (`var(--border)`, `bg-primary`, `text-muted-foreground`, etc.).

## Definition of done

A change is done when all of the following hold:

1. **Works in the real app** — verified via `bun run dev` (or a build), not just type-checked. Run it and confirm the change renders/behaves.
2. **Type-checks and lints clean** — `bun run lint` passes; no new TS errors. (The project has no standalone `tsc` script; Vite/editor surfaces type errors.)
3. **Follows the conventions** in this file: strict-TS idiom, `@/` alias, `cn()`, why-comments, no `any`.
4. **Respects the architecture** — AI/Azure/Node code stays server-side; client bundle is untouched by secrets; shared types live in `src/lib/types.ts`.
5. **Preserves graceful degradation** (for anything AI/Azure): if a cloud dependency is unavailable, the feature must fail visibly and recoverably (typed error + clear message), not crash the page.
6. **No mock-data entanglement** — new features must not silently depend on `mock-data.ts` unless clearly UI-only; the mock layer is meant to be replaced by the Aasrith server implementation.
7. **Does not rewrite published git history** (Lovable constraint).
8. **No test suite exists to break**, but any new pure logic should be written test-friendly (pure functions, explicit inputs) so tests can be added later.

## AI engineering principles

These are the non-negotiables for any AI feature in this project:

1. **LLM output is untrusted data.** Always coerce/validate against a schema (`coerce()`-style helpers or zod). Never let raw model output reach the UI or database.
2. **Deterministic signals first, LLM as a signal — never the sole source.** Keyword + embedding evidence must be computable without an LLM, so scoring remains auditable and cheap. The LLM refines and explains; it doesn't replace the deterministic pass.
3. **Evidence over assertion.** Every score/verdict must be traceable to a quoted source (resume section, keyword, requirement). The model is explicitly instructed to never claim evidence that isn't in the resume ("Never claim evidence that is not there").
4. **Cost-bounded by design.** Expensive per-candidate LLM calls run best-first over a configurable limit (`SCREENING_AI_ANALYSIS_LIMIT`). Never send unbounded pools through an LLM.
5. **Graceful degradation is a product feature.** With no Azure credentials, the app must still work (heuristic parsers, keyword matching) and clearly label which engine produced each result.
6. **Structured outputs with fallback.** Prefer JSON-schema-constrained responses; degrade to `json_object` mode; salvage JSON from prose with a tolerant extractor.
7. **Blind-review integrity:** if blind mode is a hard guarantee, PII must be stripped before any LLM analysis; otherwise blind mode is UI-only and that limitation must be documented.
8. **Copilot is a tool-using agent (target), not a string-matcher.** The current rule-based `answer()` is a placeholder to be replaced by an agent with structured tools over screening data. Keep the same no-fabrication discipline.

- [ ] **Am I about to rewrite git history?** Stop — Lovable forbids it. Create a new commit instead.
